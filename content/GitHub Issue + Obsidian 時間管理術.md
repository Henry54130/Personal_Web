> [!summary] core：
> 讓 Obsidian 回歸指揮，讓 GitHub 負責行動。透過將「動態任務」從「靜態筆記」中物理隔絕，徹底終結管理熵增。

---

## 1️⃣ 痛點：消失在 ## WIP 區塊裡的專案與意志力

我曾是個 Obsidian 「全能管理」的信徒。我習慣在每個專案筆記（如：MEMS 報告、越南語學習）的最上端，開一個 `## WIP` 或 `## TODO` 區塊，記錄所有的待辦事項。而在旁邊@日期@人@地點...

這看起來很完美：知識與任務都在同一個頁面，「所見即所得」。但當專案從 3 個變成 10 個，這套系統產生了嚴重的**行動摩擦**：

*   **痛苦的「開箱巡邏」：** 每天早上我不是開始執行，而是得像保全一樣，一個一個點開 10 個專案筆記，確認WIP「今天有沒有要動手的事」。
* 如果你不只是純文字清單，還一個個連結成task.md
	*   **搜尋污染與噪音：** 當我想要搜尋學術原理時，搜尋結果全是細碎的待辦清單，知識與雜訊混在一起。

## 2️⃣ 解法：實施「政經分離」——資訊流的重新分配

核心哲學：**將「思考（靜態知識、資料）」與「執行（動態行動）」物理隔離。**

### 📍 Obsidian 的定位：專案的「終端」與「大腦」
我提取了所有筆記裡的 `## WIP` 區塊，讓 Obsidian 回歸它最強大的功能：**知識沉澱**。
*   **它是圖書館：** 存放文獻、技術文件、會議記錄與決策脈絡。
*   **它是終端機：** 所有資源連結、文件連結都由此出發。
*   **它不再是戰場：** 這裡不再存放任何有「時效性」的瑣碎任務區塊、連結，保持筆記庫的純淨。只透過連結，連結到相關的issue。

### 📍 GitHub Issue：地表最強的動態任務資料庫
我把所有的「執行層」全部搬到了 GitHub Issues。
（我的設計架構參考：[[github issue 父子架構管理專案及任務]]）

**為什麼 GitHub 是更好的選擇？**
1.  **資料結構化：** 任務在 GitHub 是「資料庫欄位」。透過 `gh` CLI，任務會「主動」在正確的時間點推播到我的 Daily Note。(可以自己寫定時的py script，或者你就點開issue就好XD)
2.  **我的設計架構簡介：** 
    *   **時間相關欄位：** 監控「三道防線」（Target/Due Date），確保緩衝區安全。
    *   **type：** 有project,task,activity...
    *   **自動化掛鉤：** 利用 API 實現任務與 Daily Note 的聯動，減少決策損耗。(順便說，我喜歡每天只看Daily Note：裡面有紀錄、提醒我當天日程、任務、以及寫日記的空間...)

## 小結
> [!summary] 最終的哲學：
  >
  「工具的價值，不在於它能幫你做多少事，而在於它能為你的大腦省下多少頻寬。」

  讓 Obsidian 回歸思考，讓 GitHub
  負責行動。  讓我們一起殺掉那些無效的巡邏，找回真正屬於早晨的專注力！
